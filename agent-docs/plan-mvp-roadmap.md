# SL Fake Bets — Path to MVP Roadmap

Phased execution plan from the current frontend-only prototype to the `[mvp]` requirement set running against a 100%-local Supabase backend. Produced 2026-09-04 from a multi-agent map → propose (3 angles) → judge → synthesize pass over the codebase, `vision.md`, and `AGENT_SPEC.md`; revised the same day after a 3-agent verification audit (shared package, web app, spec/vision) — see §7.

**How to use this doc:**

- Each phase below is sized for ONE fresh agent session (roughly ≤ ~15 files / one subsystem). Start a new session per phase; the phase's Goal + Tasks + Exit criteria are written so the session can execute from this doc alone. A phase is done only when every exit criterion is verified. Do not start work from a later phase early.
- **Phase-numbering trap:** "Phase 1–9" in this doc is this roadmap's own breakdown. The spec and vision use a DIFFERENT 3-phase vocabulary (ARC-010/011/012: vision Phase 1 = frontend-only mock, Phase 2 = fully local backend, Phase 3 = hosted backend), and code comments like `title="Phase 1 — not wired"` use the VISION numbering. Roadmap Phases 1–2 live inside vision Phase 1; roadmap Phase 3 executes the vision 1→2 transition.
- Before writing code, read the spec IDs the task cites (`agent-docs/AGENT_SPEC.md`), §4's open-point decisions, and any shared module a task says to reuse.
- Standing constraints the current frontend already satisfies — preserve, don't rebuild, don't regress: UX-008 (bet ordering: open first, soonest-closing first), UX-009/010/011 (team selector / full re-scope on switch / returning users land on the default team dashboard), UX-014/015/016 (modal-first policy; bet detail is the only full page), UX-020/021 (black/white + jade identity; "SL", never "Soulless"), UX-025 (responsive), UX-026 (English-only), DOM-030 (no content moderation), ARC-014 (zero notifications).

## 1. Current state (as mapped and audit-verified 2026-09-04)

- Stack: Turborepo + pnpm workspaces; Next.js 16.3.4 App Router in `apps/web` with a single route `/` rendering `AppGate`; root scripts `dev`/`build`/`lint`/`typecheck` exist exactly as spelled. **No test runner is installed anywhere in the monorepo** (no vitest/jest, no `test` script).
- `packages/shared` is a well-modeled but purely declarative domain layer: real TypeScript types, one genuinely reusable pure function (`getPoolStats` in `pari-mutuel.ts` for pari-mutuel odds), a frozen `CONFIG` (`ONBOARDING_GRANT_COINS: 100`, `DAILY_REWARD_COINS: 5`, `TEAM_TARGET_SIZE: 30`, `BET_DURATION_PRESETS` 1h/24h/7d; plus standalone `DEFAULT_MAX_WAGER`), and deterministic mock fixtures — but zero validation, settlement, ledger, permission, or ID-generation logic.
- `Transaction["kind"]` is a closed union: `"onboarding-grant" | "daily-reward" | "injection" | "donation"`. There is NO kind for wager stakes, payouts, or refunds — matching DOM-025 (the ledger covers transfers/injections and is "distinct from wager logging") and DOM-026 (no per-wager audit trail; aggregated profit/loss instead). Fixture members carry hand-typed `coinBalance`/`profitLoss`; fixture transactions carry hand-typed `balanceAfter`; the fixture ledger contains no payout rows for the resolved bets. Keep this shape — see decision §4.6.
- `apps/web` has real UI plumbing: modal stack, team switching, hydration-safe auth gating, live pari-mutuel math in the wager modal via `getPoolStats`, and non-trivial client-side gating already in place (create-bet blocks submit without a title + ≥2 non-empty options; wager modal clamps the amount to `min(balance, bet.maxWagerPerUser)`; delete-team already has a working type-to-confirm gate). The dashboard rail already renders wallet, standings, and rank badges from mock data (`wallet-module`, `standings-module`, `standings-full-modal`, `rank-badge`). But **every mutating action** — create bet, place wager, create team, join by code, kick/ban, inject coins, delete team, save profile (hardcoded `disabled`), leave team (no handler), resend OTP (no handler) — is a dead handler or a submit that just closes its modal. The bet-title link is a literal `href="#"` (`bet-row.tsx`).
- Auth is a single localStorage boolean (`sl:signed-in`); the "current user" is `mockCurrentUserId` (`"u-01"`); all data comes from one static fixture file (`mock-data.ts`: bets b-01–b-03 open, b-04 closed, b-05 resolved-winner, b-06 resolved-void). There is no fetch/API/DB layer of any kind.
- `supabase/` is an explicit placeholder (README only), gated by ARC-013. No `@supabase/*` package is installed anywhere yet.

## 2. MVP definition

The target of this plan is **local-MVP**: every `[mvp]`-tagged requirement in `AGENT_SPEC.md` that can be satisfied on a developer machine, running against a **100%-local** Supabase backend (`supabase start`, no cloud project):

- Real per-device auth (email OTP + Google OAuth per UX-003/ARC-006; long-lived sessions per ARC-007).
- Persistent teams, membership, and moderation (kick/ban with active-wager cascade, access-mode gating, non-expiring invite codes).
- Persistent bets and wagers with correct pari-mutuel settlement (DOM-016/018/019), early-close (DOM-011), and hard team/bet deletion with type-to-confirm (DOM-033/034); stored per-team balances plus an auditable transfer ledger (onboarding grant, daily reward, leader injection — DOM-021/022/024/025) and aggregated profit/loss (DOM-026) — all flowing through `packages/shared`'s pure functions.
- Leaderboard, "podium of the poor", and name badges live from real balances (DOM-027/028/029).
- Profile editing incl. avatar image upload to local Supabase Storage (UX-022).
- Deep links: invite and bet-share URLs route into the join/bet flow, destination preserved through signup (UX-012).
- Realtime propagation of new bets/wagers/comments without manual refresh (ARC-005/UX-013).
- In-house `analytics_events` / `feature_flags` tables, exactly two funnel metrics (ARC-016/017; no third-party vendor).
- Dynamic OG/Twitter previews for invite and bet-share links + baseline public-page SEO (UX-017/023/024).
- The free-tier-ceilings and scale-up-path documentation the spec mandates (ARC-001/ARC-004) — written, not built.

**The one `[mvp]`-tagged item deliberately outside this plan is ARC-012** (hosted dev backend — Supabase Cloud + Vercel): it is a separate, later, owner-gated transition. Phase 9's checkpoint is therefore **"local-MVP complete"**, not "every `[mvp]` tag closed".

## 3. When the local backend starts

**Local backend work begins at Phase 3**, immediately after Phases 1–2 have made both frontend-only vertical slices (bet lifecycle; team lifecycle + comments) fully real against in-memory client state, per the vision's frontend-placeholders-first rule (ARC-010). Rationale: a durable per-device identity is the first thing the app structurally cannot fake in memory, and every later phase (persistence, ledger, realtime) depends on real identity and a real schema. Auth is deliberately its own phase (4) so Docker/CLI bootstrap friction and auth-provider friction never compete for one session's budget.

> **ARC-013 gate — read before Phase 3.** Naming Phase 3 as the transition point is **not** the owner's authorization to run it. In vision numbering, roadmap Phase 3 is the Phase 1→2 transition (ARC-011), exactly what ARC-013 gates: *"never advance a phase (1→2, 2→3) without the owner's explicit instruction for that specific move, in that moment."* Before any Phase 3 command (`supabase init`, `supabase start`) executes, the owner must give a separate, explicit, in-the-moment order for that specific transition. Finishing Phases 1–2 does not auto-authorize it. The same gate applies again, separately, to the future hosted-backend transition (ARC-012).

## 4. Open spec points this plan resolves (owner may overrule)

`AGENT_SPEC.md` leaves several points explicitly or implicitly open. Executing sessions follow these defaults — do not silently re-decide them differently; each is cheap to change if the owner overrules:

1. **Email auth flavor = OTP code.** ARC-006 leaves magic link / OTP / password open; OTP is the lowest-friction flavor that also works cleanly against `supabase start`'s local mail sandbox (Inbucket/Mailpit). **Suspended for early access, 2026-09-07** (D1, `plan-hosted-early-access.md`): the hosted free tier's built-in mailer cannot reach anyone outside the project's own Supabase team, so the hosted early access ships password login instead; OTP returns at full release with an SMTP vendor.
2. **Onboarding grant is per team membership, applied on create/join.** DOM-021 phrases the grant per-user ("new users get…"), but DOM-013 makes balances per-team and `Transaction` requires a `teamId` — a signup-time grant has nowhere to land, and the spec never resolves this tension (it is not in its own open-decisions list). Default: every new membership starts at `CONFIG.ONBOARDING_GRANT_COINS` via an `"onboarding-grant"` transaction — which is exactly what the fixtures model.
3. **Daily reward is per (user, team, calendar day), granted lazily on team load.** DOM-022 flags unconditional-vs-only-when-broke as ambiguous; spec default A-2 says unconditional. Per-team scoping follows the same rationale as #2.
4. **Kick/ban wager cascade = remove the member's wagers from all active pools.** DOM-032 mandates the removal but explicitly leaves refunded-vs-forfeited-vs-removed open. Since the per-team balance is deleted along with the membership, "refund to the removed member" has no durable target; plain removal is the default — pools shrink and everyone else's odds recompute automatically because `getPoolStats` runs over live wagers. The cascade must still go through one shared `settlement.ts` helper so the Phase 2 in-memory version and the Phase 5 RPC behave identically.
5. **Bet options floor = 2, no maximum.** DOM-007 says options are plural but marks min/max count open.
6. **Ledger scope stays spec-literal (DOM-025/026).** Transactions = grants/rewards/injections (the `"donation"` kind stays reserved for post-MVP DOM-023). Wager stakes, payouts, and void refunds mutate stored balances + aggregated `profitLoss` via `settlement.ts` and are **not** ledger rows — do not extend `Transaction["kind"]`, do not event-source balances by replaying history. Balances are stored on the member (per types + fixtures) and updated atomically with each mutation.
7. **Onboarding = one skippable full-screen profile step, after the team step, once per account.** UX-001/002/028 mandate a low-friction, pre-filled, step-structured onboarding but never say what the steps *are*. Default (owner-ordered 2026-09-05, specified in Phase 7.5): signup → team (create/join) → confirm-your-profile → dashboard, where the profile step is never required, is skipped in one click, and is marked done by `users.onboarded_at` whether it was saved or skipped.
8. **Team chat is 30-day, device-local, Postgres-Changes, two-surfaced.** UX-019 was `[future]` and on §6 risk 7's exclusion list; the owner ordered it built on 2026-09-06, after the local-MVP checkpoint, as **Extra Phase 1 (§8)**. Four rulings taken with it — 30-day hard retention; a `localStorage` last-seen marker rather than a `last_read_at` column (so the unread divider is per-device by design); Postgres Changes rather than the §4.3 Broadcast escape hatch; and a live rail module *plus* a full-scrollback modal sharing one store. Rationale for each is in §8; this entry exists so a session reading only §4 does not re-open them.
9. **A 1v1 duel is a `kind` of bet, not a new bet lifecycle.** The owner ordered 1v1 bets on 2026-09-06 and asked explicitly for an architecture that absorbs future features without a rewrite; the answer is a `bets.kind` discriminator plus a `bet_duels` side table, with `bets.state` and its no-escape-hatch transition trigger untouched. Eight rulings were taken with it and are written out as D1–D8 in **Extra Phases 2 and 3 (§8)**: the kind-plus-side-table shape (D1); "waiting to be accepted" expressed as `accepted_at IS NULL` on an `open` bet whose `closes_at` *is* the accept deadline (D2); a `void_reason` enum so history can say *why* (D3); re-ordering the feed instead of notifying anyone (D4); the challenger debited at creation and the challengee at accept, with insufficient funds refusing the accept outright (D5); the creator barred from resolving their own duel and from deleting it once accepted (D6); any teammate as mediator with "any moderator" additive rather than exclusive (D7); lazy, twice-enforced expiry because no scheduler exists on this stack (D8); and — overruling this plan's first draft — **DOM-002 does not gate duels at all**: a restricted team lets anyone challenge, and forces `any_moderator` on at creation instead, so the leader keeps a resolver guarantee rather than a veto (D9). This entry exists so a session reading only §4 does not re-open them. **Unlike #8, this lifts nothing from §6 risk 7** — the feature has no requirement ID in `AGENT_SPEC.md` at all.
10. **A toast is a caller-initiated acknowledgement; a notification is not, and the two are separated by rule.** `design-visual-identity.md` §5.9 has specified a toast since before Phase 1, but the app had none until Extra Phase 1 needed one, and §5.9 leaves four things open that a real system has to answer. The owner ruled on them on 2026-09-06, before **Extra Phase 4 (§8)** was written: a global provider with a portalled layer rather than per-surface local state (D1); all nine toast-worthy call sites wired in one phase rather than the system plus one consumer (D2); §5.9's never-used ember rail built and given the six destructive-action confirmations (D3); and the 3.5s dismiss becoming a caller override that still defaults to exactly 3.5s (D4). Six further rulings were resolved in-plan and are written out as D5–D10 in the phase — the one that matters outside it is **D5**, which turns Extra Phase 3's risk 4 into a rule: a toast may only be raised synchronously in the handler of an action the person themselves took. A toast fired from a realtime handler, a stack that persists across a reload, or any list, count or badge of past toasts is the notification system ARC-014 has excluded through nine phases. This entry exists so a session reading only §4 does not re-open them.

> 6. **`addTransaction` was removed from the context's public API**, replaced by the gated `injectCoins` — an ungated ledger writer next to `canInjectCoins` is a footgun, and nothing consumed it. Phase 5's RPC set matches the mutator names one-for-one.

**The UX decision (owner asked for the best-practice call; this is it):** a **full-screen step between `TeamGate` and the dashboard**, not a forced modal, and not a blocking form.

Why this shape, point by point — the implementing session must preserve the reasoning, not just the file list:

- **A gate, not a forced modal.** `team-gate.tsx` already states the rule this follows: *"deliberately NOT the create-team modal — a modal implies something behind it to go back to, and here there is nothing."* A modal auto-opened over a dashboard the user has never seen is the worst of both worlds: it dims content they cannot read yet, and its close affordance (an X in the corner) reads as *dismiss and lose*, not as *skip*. A step owns the viewport, so the skip control can be a real, labeled, primary-weight button.
- **After the team step, not before it.** A new arrival gets here two ways, and both are better served by profile-last: the invite-link visitor came to join a specific team (`join-page.tsx` already `router.replace("/")`s into the dashboard route on success, so the gate catches them on the very next render), and the cold-start visitor came to make one. Interposing a name-and-color screen before either is a decision between the user and the thing they clicked — precisely what UX-001 forbids. Profile-after also means the step can frame itself as *"this is how your team sees you"*, which is the only reason to care about the field, and it puts the whole feature below `TeamGate`, where `useTeam()` already hands over `currentUser` and `updateProfile`.
- **Confirm, never fill.** Every field arrives pre-filled and valid from Phase 4's `app.handle_new_user` (UX-002), so this step has **no required input and no validation wall**. Show a live identity preview (`UserAvatar` + name in the chosen color) so a second's glance is enough to decide.
- **Skip prominence is conditional on prefill quality** (the owner's explicit requirement). Phase 4's `app.default_display_name` already ranks its sources: Google's `full_name`/`name` is a *real* name, while an email local part or the `'Player'` literal is a placeholder the user has never seen and did not choose. Editing is one visibly-available secondary action away, on the same screen. A user who signed in with Google reaches the dashboard in one click.

### Phase 8 — Realtime propagation ✅ COMPLETE (2026-09-05)

**Goal:** close the liveness gap (ARC-005/UX-013, extended to UX-018's comments): bets, wagers, and comments propagate to other online team members without manual refresh, using **coarse-grained** Supabase Realtime subscriptions only.

**Read first: `agent-docs/design-realtime.md`** — the cost/mechanism analysis run on owner request before this phase (2026-09-05), with quotas re-verified that day. Its §5 rules are binding here; tasks 0, 2 and 5 below exist because of it. The one-line version: Realtime is free for this app by two orders of magnitude and polling would blow the 5GB egress ceiling in under two days, but **only** because payloads stay small — a subscription handler that refetches the world costs more than the polling it replaced.

**Tasks:**
0. **Publication migration first — nothing fires without it.** `supabase/config.toml` starts the Realtime service, but no migration has ever run `alter publication supabase_realtime add table ...`, so Postgres Changes is silently inert today: subscriptions connect, report `SUBSCRIBED`, and never receive an event. Add `bets`, `wagers`, `comments` to the publication (and only those — see task 5), plus `replica identity full` on any of them whose UPDATE old-values or DELETE payload the client needs; by default those events carry the new record only. Do this before writing any client code, or the whole phase debugs a working subscription against a dead publication.
1. Coarse-grained subscriptions only: one per-team channel for the bet list, one per-bet-page channel for wager/comment updates. **Use Postgres Changes, not Broadcast** — Supabase now recommends Broadcast for scale because Postgres Changes authorizes every event against each subscriber on a single ordered thread (~3,000 msg/sec ceiling), but at ~15–60 subscribers and ~300 changes/day this app uses ~0.001% of that, and Broadcast would mean writing trigger functions for a problem it will never have. Broadcast-from-database is the documented escape hatch and belongs in Phase 9's ARC-004 scale-up doc alongside the 200-connection / 2M-message free-tier ceilings, not in this phase.
2. Wire `team-context.tsx` and the bet-detail page to live-update on relevant INSERT/UPDATE events **by applying the event's own payload**. A handler must not call `reload()` as its normal path: signal-only realtime (event arrives → refetch the world) costs ~18GB/month against a 5GB ceiling, worse than the polling it would replace, because `loadTeamData` pulls nine unbounded queries including the entire `transactions` ledger. A full reload stays legal as *recovery* — resubscribe after a dropped connection, or a payload the client cannot reconcile — never as the design.
3. Subscription lifecycle: subscribe once per mounted team/bet context; tear down cleanly on unmount/team switch; guard races between a just-arrived realtime event and an in-flight manual refetch.
4. Verify channel-count discipline in the local Realtime inspector matches the coarse granularity (per team/bet-list/bet-page — never per-row/per-field).
5. **Do not subscribe to `team_members` or `transactions`, and do not add them to the publication.** One `resolve_bet` updates ~30 balance rows at once — 30 changes × 15 subscribers = 450 messages from a single resolution, more than a normal day of bets, wagers and comments combined. It is also exactly where the double-apply race warned about in Phase 7's notes bites: `resolve_bet` and `delete_bet` already return their deltas and the acting client already dispatches them, so replaying `team_members` UPDATEs would apply the same move twice. Propagate balances by deriving them from the bet's resolution event, or by one scoped refetch triggered by it.
6. **Handle the DELETE hole.** RLS is not applied to DELETE events — Postgres cannot verify access to a row that no longer exists — so a `delete_bet` broadcasts to every subscriber of the channel regardless of team. The mitigation is behavioural, not a policy: ignore any id the client does not already hold.

- No subscription handler triggers a full `loadTeamData` on a normal event — grep the phase's diff for it and confirm each surviving call is a recovery path.
- A bet deleted in another team produces no visible effect in a session that never held it.

What a later phase needs to know:

- **The publication is the whole server side, and it is idempotent.** `20260905190000_realtime_publication.sql` adds `bets`, `wagers`, `comments` — nothing else, per §5 rule 3 — inside a `do` block that checks `pg_publication_tables` first, so a `db reset` and an out-of-band apply behave the same. **Replica identity stays at the default (primary key)** and the migration header says why: the client compares an UPDATE's NEW record against the copy it already holds, and a DELETE's primary key *is* the entire message it needs. `replica identity full` would double the WAL volume of every wager and comment for information nothing reads.
- **A `bets` INSERT does not carry `bet_options`, so a new remote bet costs exactly one scoped single-row fetch** (`fetchBet`, sharing `BET_SELECT` with the full load). This is the only read any handler performs and it is what §5 rule 2 permits — a row, not the world. The alternative (adding `bet_options` to the publication) was rejected: it trades one round trip for an ordering problem between a bet and its options.
- **Two invariants carry every handler, and the second one does three jobs.** Apply the payload, never refetch; and *ignore any id you do not already hold*. That single guard drops the DELETE events RLS cannot filter, drops the acting client's echo of a change it has already applied — which is what keeps money from moving twice — and makes at-least-once delivery harmless. The three insert actions in the reducer were additionally made idempotent on the row id, so the property does not depend on five callers remembering it.
- **Balances propagate without `team_members` ever being subscribed.** A remote resolution recomputes the deltas with `settleBet` over wagers this client received on the same channel; a remote delete unwinds with `reverseBet`. Both are the pure functions the RPCs are SQL twins of, so the derived move is the move Postgres made. Verified in the browser: a stake placed by session A, closed and resolved by session B, settled live on A's screen with no reload and no consistency-guard complaint.
- **`bets` DELETE is registered WITHOUT a team filter, deliberately.** With the default replica identity the payload has only the primary key, so a `team_id=eq.` filter would match nothing and the event would never arrive — the filter would look like a security boundary while silently disabling the feature. Confirmed both halves in the wire harness: an unrelated team's session *does* receive the delete (the documented RLS hole, §4.3), and a third browser signed into another team showed no visible change at all, because it never held that id. INSERT/UPDATE on `bets` and INSERT on `wagers`/`comments` are correctly scoped by RLS — the outsider received none of them.
- **The reload race is queued, not hoped away.** `loadTeamData` is nine round trips wide; an event landing inside that window would otherwise be overwritten by a snapshot that predates it. Events arriving while a load is in flight are held in a ref and replayed after the `replace` commits, and the id guards make replaying something the snapshot already contains a no-op. `dataRef` is synced in an effect rather than during render (the `react-hooks/refs` rule is right: network callbacks cannot fire before the commit that produced the state they would read).
- **Channel lifecycle is keyed on `team.id`, never on `team`.** The team object's identity changes with every state patch; a channel keyed on it would resubscribe on every incoming wager and drop events in the gap it opened. Verified by reading the tab's own WebSocket frames over CDP: rapid switching across three teams produced a strict `phx_leave` → `phx_join` alternation, never two team channels at once, never a topic joined twice, exactly one team channel open at rest. Channel count matches the coarse design: one `team:<id>` plus, on the bet page only, one `bet:<id>`.
- **The bet page's channel carries comments only** — bets and wagers already arrive on the team channel into the same store — and it is subscribed *before* the not-found branch, so a bet created moments ago in another session resolves instead of dead-ending. In dev you will see `bet:<id>` join, leave and join again: that is React StrictMode double-invoking the effect, and the net result is one channel.
- **No handler reloads on a normal event.** The surviving `reload()` calls are: identity change, `createTeam`/`joinTeamByCode` (both re-scope the world), and `onResubscribe` — the recovery path §5 rule 2 explicitly allows, fired only on a *re*-subscribe after a connection actually dropped, never on the first SUBSCRIBED.
- **Wager DELETEs are deliberately not handled.** Only two things delete wagers: `delete_bet`, where the money is unwound from the bets DELETE event and the wagers must still be present to compute the reversal (cascade children replicate *before* their parent, so consuming them first would silently zero the refund) — and the kick/ban cascade, whose companion `team_members` change is not subscribed at all. Applying half of either is worse than applying neither; the pool corrects on the next load. This is the one known staleness window the phase leaves open, and it is recorded in `realtime.ts` beside the code.
- **Harness traps, for whoever automates the UI next.** The dashboard renders its own "Create bet" (the FAB) and "Wager" buttons *behind* an open modal, so a `find`-first click hits the wrong one — click the last match, or scope to the overlay. Sign-in must click `button[type=submit]`; a text match on "continue" hits "Continue with Google" first. Mailpit (not Inbucket) serves the local mail on :54324, API `/api/v1/search?query=to:…`. `[auth.rate_limit] email_sent = 2` per hour still applies — sign in at most two accounts per hour or the OTP mail silently stops.

**Six defects the audit found in the shipped code**, none of them blocking, all of them things a later session would otherwise re-discover the hard way:

1. **The 30-day window is app-code discipline, not a database boundary.** Task 2 orders `grant select, insert, delete` on the table *and* task 5b orders the window predicate on "every read" — the migration obeyed both literally, so a member issuing a plain PostgREST `select` on `public.chat_messages` reads 31-day-old rows the pruner has not yet deleted. The exit criterion "invisible to every read before the pruner has run" is true only of reads routed through `chat_page`, which is every read the *app* makes. Closing it means either dropping the direct SELECT grant or putting the time predicate into `chat_messages_select_team_member`. **This is as much a plan defect as an implementation one** — the two instructions cannot both be followed and still produce the guarantee the header claims.
2. **The body CHECK is not the validator's twin on three axes.** `check (length(btrim(body)) > 0 and length(body) <= 500)` measures the *untrimmed* body, `btrim` strips only U+0020 where JS `.trim()` strips all whitespace, and Postgres `length()` counts code points where JS `.length` counts UTF-16 units. `CONFIG.CHAT_MESSAGE_MAX_CHARS`'s "the two must never drift" is a promise about the number 500, not about the bound. The one live consequence is inside `chat-thread.tsx`: the composer counter reddens on raw `body.length` (`:247`) while the send gate uses the trimmed validator (`:249`), so "505/500" can render in `text-negative` beside an enabled send button whose write then succeeds. 300 astral emoji is the mirror case — the database would store it, the client will never send it.
3. **The "N new ↓" pill counts prepends.** Both surfaces compute it as `chat.messages.length − awayBaseline`, and `loadEarlierChat` grows that same length from the *front*, so paging back can read "50 new ↓" for messages older than everything on screen — and inflates every genuinely-new count afterwards until the reader returns to the bottom. It crosses surfaces: a page loaded in the modal inflates the rail's pill, because they share the slice by design. The fix is to count against a stable newest-row id, not a length.
4. **`hasMore` compares against the *requested* limit** (`rows.length === limit`) while `chat_page` clamps server-side to `least(greatest(coalesce(p_limit, 30), 1), 100)`. Latent, not live — the only callers pass 30 and 50 — but any future caller passing >100 gets a permanent `hasMore: false` and silently stops paging. The 100 is an undocumented implementation addition; the plan asked only for 30 and 50.
5. **A realtime insert can be dropped in the `"loading"` window.** The `chat-insert` handler correctly discards events while the slice is `"idle"` (nothing is loaded, so nothing is lost), but an insert arriving after `fetchChatPage`'s snapshot and before the `loaded` dispatch is appended and then overwritten by `loaded`'s wholesale `messages:` replacement. Narrow, and self-correcting on the next page load, but real.
6. **`infra.ts`'s amended flag comment replaced one stale claim with a wrong one.** It now asserts `global-team-chat` gated the stub before this phase and that "the stub carried both flags at once" — neither is true: before `6181640` the flag was a bare union member with zero readers and a `false` seed, and only `coming-soon-teasers` ever gated the stub, whose `SOON` badge was a hard-coded span. #### Owner decisions (2026-09-06) — taken before this phase was written, do not silently re-decide

- **D1 — A duel is a `bets` row with a `kind`, plus a side table. Not a new state, and not a fourth column set on `bets`.** The owner asked for an architecture that absorbs future features without a rewrite, and this is the shape that does: `public.bet_kind` (`'pool' | 'duel'`) is the discriminator, and everything kind-specific lives in `public.bet_duels` (1:1 on `bet_id`). A future kind is one enum value plus one side table — never a migration that widens `bets` with another six nullable columns that 99% of rows ignore. **`bets.state` is not touched and `enforce_bet_state_transition` is not widened**; it is the only trigger in the schema deliberately built with no service-context escape hatch, and this phase leaves it that way.
- **D2 — "Waiting to be accepted" is `kind='duel' AND accepted_at IS NULL AND state='open'`, and the existing clock carries it.** On create, `closes_at` is set to the accept deadline, so UX-008's sort, `computeEffectiveState` and the countdown all work with no special case. On accept, the duel does exactly what `close_bet_early` already does — `state='closed'`, `closes_at=now()` — and lands in the `AWAITING RESULT` state the design system already specifies. Decline, expiry and pre-acceptance deletion each run `open→closed→resolved` as two legal hops inside one transaction. **Every DOM-012 transition stays legal; none is invented.**
- **D3 — Voids gain a reason, and it is an enum.** `public.bet_void_reason` (`'mediator' | 'declined' | 'insufficient-funds' | 'expired' | 'participant-left'`), nullable on `bets`, `NULL` for every pool bet and every void that already exists — so no backfill. It exists because the owner requires the history row to say the challengee *couldn't afford it*, and it is an enum rather than free text because the next feature that voids a bet for a new reason should add a value, not a string convention. A void is still a void: full refund, zero realized P/L, the `VOID · REFUNDED` treatment. The reason is a suffix, never a second state.
- **D4 — Nobody is notified; the feed is re-ordered instead.** ARC-014 is untouched: no push, no email, no bell, no tab title. A duel awaiting *your* acceptance sorts to the top of its group for *you* and carries a distinct row treatment (Extra Phase 3, task 6). The same rule extends to the mediator when a duel awaits *their* ruling — the owner's instruction named the challengee, and this is its obvious completion; it is recorded here rather than assumed, because it widens a rule the owner wrote.
- **D5 — Money moves twice, never on credit.** The challenger's stake leaves their balance the moment they send the challenge (a real `wagers` row on their own side, through the same lock-then-debit sequence as `place_wager`); the challengee's leaves on accept. Stakes are symmetric — one amount, chosen by the challenger. If the challengee cannot cover it at accept time, **accept is refused** (DOM-014 is absolute) and the decline path is offered instead, carrying `void_reason='insufficient-funds'`. No escrow account, no held-balance column: the coins are simply gone from the challenger's balance and come back on any void, exactly as `reverseBet` already returns stakes.
- **D6 — The creator of a duel may not resolve it, and may only delete it before it is accepted.** `app.can_manage_bet` today answers `close_bet_early`, `delete_bet` *and* `resolve_bet` with one rule — creator-or-moderator — which on a duel would let a challenger both judge and destroy their own losing bet. Resolution forks into a new helper; deletion keeps the old one plus an unaccepted-only guard; early close is refused outright for a duel, because a bet nobody may wager in has no wagering window to close.
- **D7 — The mediator may be any teammate, and "any moderator" is additive.** The named mediator is anyone on the roster except the two participants. Ticking *any moderator* does not replace them: whoever acts first resolves it, so a duel is never frozen behind one quiet person. A moderator who is a participant is excluded from the any-moderator pool by the same rule that excludes the creator.
- **D9 — A restricted team does not block duels; it forces `any_moderator` on instead** (owner ruling, 2026-09-06, overruling this plan's first draft). `canStartDuel` is plain membership — **not** `canCreateBet`, and DOM-002 does not gate it. A duel is a private arrangement between two people who have already agreed to it, not a bet posted for the team to wager into, so the access mode has nothing to ration. What the leader keeps instead is a guarantee: any duel created while the team is `restricted` stores `any_moderator = true` regardless of what the challenger ticked, so a moderator can always step in and resolve it. The named mediator is still allowed alongside (D7 is additive), and the control renders checked-and-disabled with the reason.
  - **Enforced at creation, never retroactively.** Flipping a team to `restricted` does not rewrite `any_moderator` on duels already in flight, and flipping it back to `free-for-all` does not withdraw it. The stored row stays the truth about who may resolve *that* duel, so a live duel's resolver set cannot change under it because someone opened team settings. `create_duel` is the single place the rule applies — it reads the team's access mode inside the same transaction that writes the row.
- **D8 — Expiry is lazy and enforced twice.** ~~because there is no scheduler. No `pg_cron`, no extension of any kind, is installed on this stack (verified: zero `create extension` statements across all 14 migrations)~~ **Premise corrected 2026-09-06, after Extra Phase 1 shipped: a scheduler now exists.** That migration is the 15th and the first to carry a `create extension` statement — `pg_cron` 1.6.4 is installed and running a nightly `prune-chat-messages` job. (The original parenthetical was also a bad inference even when written: a grep for `create extension` says nothing about what the Supabase base image already provides, and `pgcrypto` was in use from Phase 3's `gen_random_uuid()` default.) **The decision itself is unchanged and this phase still installs nothing**, because its real justification never was the absence of a scheduler — it is Extra Phase 1 task 5's own sentence, that retention which depends on a scheduler is retention that silently stops the first time the scheduler does, on a deployment that pauses after 7 idle days. A duel's money is a stronger case for that rule than chat's, not a weaker one. Do **not** read the correction as licence to schedule the sweep: the pattern below is exactly `computeEffectiveState`, **(a)** every read treats an unaccepted duel past `closes_at` as void, so the UI is never wrong even if nothing has run; **(b)** `app.expire_stale_duels(p_team_id)` persists the void and the refund, swept opportunistically on team load and before every duel write. (a) is what makes the feature correct; (b) is what makes the money real.

4. **A guard the plan did not name:** `resolve_bet` refuses an unaccepted duel with *"This duel hasn't been accepted yet."* Without it a mediator could declare a winner on a one-sided duel — `app.settle_bet` would find the single wager, make its option the winning side, hand the challenger their own stake back at zero P/L, and leave a resolved bet that never happened.
5. **`app.void_duel`'s first hop writes `closes_at = least(closes_at, now())`.** DOM-012 defines `closes_at` as the moment open→closed happened. A decline closes the bet *now*; an expiry closed it at a deadline already past. `least` picks the right one without branching.
6. **`create_duel` evaluates the resolver rule against the *coerced* `any_moderator`.** In a restricted team a call with `mediator = null, any_moderator = false` is therefore accepted and stored as `true` rather than refused — the literal reading of D9, which says a restricted team *forces the box on* rather than rejecting the draft.
7. **The pending cap is swept before it is counted.** D8's sweep runs at the top of `create_duel` as well as `accept_duel`; without it a long-expired challenge still has `accepted_at IS NULL` and would occupy one of the challenger's three slots forever.
8. **`sweep_stale_duels()` is awaited *before* `loadTeamData`'s parallel batch, not inside it.** A sweep landing mid-read would hand the client a bet still reading `open` beside members whose balances had already been refunded, and the Phase 7 consistency guard reports exactly that as drift. It costs one round trip on cold start; half (a) (`computeDuelPhase`) is what keeps the feature correct if the call fails, and the ordering is what keeps the *snapshot* coherent.

**Two defects found by driving the exit criteria, both fixed in `20260906130400_duel_pair_rule_fix.sql`:**

1. **A single decline locked two people out of each other permanently — and the defect was in this plan, not only in the code.** Task 9 asks for an index making a second *pending* duel from the same challenger to the same challengee impossible. What shipped was `unique (challenger_id, challengee_id) where accepted_at is null`, and *unaccepted is not pending*: a declined, expired or cascade-voided duel is resolved on `bets`, but its `bet_duels.accepted_at` stays NULL forever, because nothing ever accepted it. Reproduced live — A challenges B, B declines, and every later challenge from A to B came back with *"You already have a challenge waiting for an answer from them."*, a sentence that is simply false about a duel that was answered. Both PL/pgSQL copies of the rule had been written to match the index's predicate rather than the roadmap's, on the sound principle that three enforcement points disagreeing is worse than one being wrong — so all three were wrong together, and the pre-checks produced a readable sentence instead of a raw `23505`, which is why nothing looked broken. **The index is dropped rather than narrowed**, because the correct predicate needs `bets.state` and a partial index cannot reference another table; mirroring that state onto `bet_duels` was rejected as the duplicated column this schema's own header warns against. The race it guarded is now closed by the `team_members` `FOR UPDATE` lock `create_duel` already took for its debit, moved above the two checks it now also protects — both are per (challenger, team), which is exactly what that row lock serialises. The pair rule is also team-scoped now, for the same reason the cap always was. **Credit where due: `20260906130000_duel_schema.sql` documented this limitation on the index itself and explicitly declined to fix it unilaterally**, which is why it was found in minutes rather than by a member months later.
2. **`anon` held EXECUTE on every duel RPC** — `create_duel`, `accept_duel`, `decline_duel`, `sweep_stale_duels` and the recreated `resolve_bet`. Exactly the trap `20260906120000_team_chat.sql` documented for `chat_page`: this schema's `ALTER DEFAULT PRIVILEGES` grants EXECUTE to `anon` **by name** at CREATE time, so `revoke … from public` never touches it. Not a live hole — each calls `app.require_uid()`, which raises without a JWT subject — but "it fails a line later" is not a reason to leave a money-moving RPC callable by the anonymous role. Revoked by name.

**Driven against the live stack, not just compiled** — the gap Extra Phase 1's retro named as its own biggest, and the reason this phase's verification was done differently. Every statement below ran as a real `authenticated` role with a real JWT subject:

### Extra Phase 4 — A real toast system (§5.9) ✅ COMPLETE (2026-09-06)

**Lifts from §6 risk 7: nothing** — and this is the phase most likely to be *accused* of lifting **notifications (ARC-014)**, so the distinction is written out rather than assumed. A toast is a transient, in-app, **caller-initiated** acknowledgement of something the person just did. A notification is a message about something that happened while they were not looking. The first is what `design-visual-identity.md` §5.9 has specified since before Phase 1; the second is what nine phases have held out. Extra Phase 3's own risk 4 already names the exact way this phase could go wrong — *"an unread count on the bell, a tab title, or a toast on arrival each cross the line"* — and the boundary D5 draws below is that sentence turned into a rule. Coin donation (DOM-023), pt-BR (UX-027), crowd resolution (DOM-020), the platform icon set (DOM-010) and native mobile are untouched.

**Goal:** replace the single-file, single-consumer, per-surface toast that Extra Phase 1 shipped with the system §5.9 actually describes — one provider, one portalled layer that survives the modal that spawned it, three rails, an accessible live region, and the **nine** call sites that currently tell a person nothing at all. The phase ends with every destructive action in the app confirming that it happened, and with `bet-row.tsx`'s share-copy no longer swallowing its own clipboard failure in an empty `catch`.

**Why it is a phase and not a chore:** an inventory of `apps/web/src` found **43 distinct feedback points**. Nine belong in a toast; **21 must stay exactly where they are** (§5.8 is explicit that a field owns its own validation error); **13 are correctly silent** and three of those carry load-bearing comments saying so. The value of this phase is as much in the 34 it must not touch as in the 9 it moves — which is why task 12 is a do-not-touch list with the same standing as the build tasks.

#### Owner decisions (2026-09-06) — taken before this phase was written, do not silently re-decide

- **D1 — A global provider and a portalled layer, not per-surface local state.** `ToastProvider` + `ToastRoot`, mirroring `ModalProvider`/`ModalRoot`, mounted once in `app-providers.tsx`. This is not architecture for its own sake: it is the only shape that fixes two present-tense defects. (a) `ModalShell`'s backdrop and the toast strip both hard-code `z-50`, and `app-providers.tsx` renders `{children}` *before* `<ModalRoot />`, so on a z-index tie the later DOM node wins and **an open modal already paints over any toast fired outside its own subtree**. (b) A kick, ban or delete confirmation is fired by a modal that closes in the same tick, so a component-local timer is destroyed before it can render. Chat got away with local state because its rail and modal are alternate views of one feature that both stay mounted; nothing else in the app is shaped that way.
- **D2 — All nine call sites, in this phase.** The six destructive-action successes (kick, ban, inject coins, delete team, delete bet, leave team), the seventh confirm-with-nothing (close bet early), `bet-row.tsx`'s share-link copy, and chat's send failure. Shipping the provider with one consumer would buy plumbing; the point of the phase is that the app stops performing destructive acts in silence.
- **D3 — The ember rail gets built and wired.** §5.9 has named three rails since before Phase 1 and the third — ember, *"destructive-confirmation only"* — has never had a consumer anywhere in the app or the roadmap. The six destructive successes are precisely that, and a ban reading as a jade *success* is semantically wrong. `ToastKind` becomes `"success" | "failure" | "destructive"`.
- **D4 — Dismiss timing is a caller override defaulting to 3500ms.** `show()` takes an optional duration; every caller that does not pass one gets exactly §5.9's 3.5s, so the doc's number stays the default rather than quietly becoming a floor. The call site is the only thing that knows whether its sentence is four words or twenty.

#### Resolved in-plan (session rulings, not owner rulings — recorded so they are not re-opened)

- **D5 — The ARC-014 boundary, as a rule rather than an intention.** A toast may only ever be raised **synchronously, in the handler of an action the person themselves took**. Forbidden by name, so no session has to re-reason it: a toast raised from a realtime event handler, from `onResubscribe`, from a polling result, from a `setInterval`, or from any background write; any persistence of a toast across a reload; any list, log, drawer or history of past toasts; any count, dot or badge derived from toasts; the notifications bell (`design-dashboard.md` §1.1) or the ARC-015 pip slot in `team-switcher.tsx` gaining a live reader. The stack cap in D6 exists partly to make the feed shape structurally awkward.
- **D6 — Stack, capped at 3, deduped by key, and no actions.** *Stack* because with nine call sites a replace-in-place model can silently eat a message the person needed; *capped at 3* because a taller stack is the feed shape D5 forbids; *deduped by key* because the realistic burst is not three different failures but the **same** failure N times — Extra Phase 1's flood trigger rejects a run of sends, and each rejection would otherwise add a row. A repeat of a live key replaces its text and restarts its timer instead of stacking. **No action affordance**, ever: §5.3 caps the screen at one jade primary, an auto-dismissing control can vanish under a keyboard user's hand mid-Tab, and the only reversible mutations in this app move money. Recovery belongs back at the control that failed — chat's composer repopulates the failed text so the person can just press send again, which is both the accessible answer and the one that needs no new component.
- **D7 — A toast may be the sole channel for a message only when the action is idempotent and its control is still on screen.** There is no notification centre and there must not be (D5), so a toast that auto-dismisses is genuinely the last time a message exists. Eight of the nine call sites are fine because the toast is *redundant by design* — it confirms a state change the person can already see (a roster row gone, a page navigated, a bet closed). The ninth, share-copy, qualifies under the idempotency half: clicking the icon again is free. Any future call site that satisfies neither half needs an inline counterpart, not a toast.
- **D8 — §5.9's rail token is corrected to `border-strong`, matching the shipped code.** The doc says the info/neutral rail is **N4**, but N4 is `--input` (`#3B403D`, 1.87:1) — one of the *surface*-elevation steps §2.1 explicitly says not to read as a boundary. Extra Phase 1 used `--border-strong` (`#656A67`, pinned to N5, documented as *"edges that must read as a boundary"*) and was right to. The doc moves to the code, with the reason recorded in the doc so the next reader does not rediscover the gap.
- **D9 — The ember rail's glyph is `/`, tinted ember — no third mark is invented.** §5.9 names three rails in one sentence and glyphs for only two in the next, which is a gap in the doc itself. The app's glyph vocabulary is exactly two marks, and a destructive action that *succeeded* is a completion, so it takes the completion mark; the ember **rail** is what says the completion was destructive. §2.3 sanctions this precisely — ember *"only fills icons, thin borders, and the one final confirm-button background"* — and a glyph is an icon. No `lucide-react` import, no check/x, per §5.9's own prohibition.
- **D10 — The live region is persistent and split by kind.** Two separate defects in the shipped component. (a) It returns `null` between toasts, so each real toast inserts a live-region node **already populated with text** — the classic dropped-announcement case. The wrapper renders unconditionally from provider mount and only its text content changes. (b) It applies `role="status"`/`aria-live="polite"` to failures as well as successes; the repo's own precedent (`auth-page.tsx`'s `Message`) already uses `role="alert"` for errors. Failure takes `role="alert"`/assertive; success and destructive take `role="status"`/polite.
