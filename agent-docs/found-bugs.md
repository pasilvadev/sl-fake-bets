## Negative balances on teammates' dashboards (display drift — Postgres is correct)

**What live actually has (prod, first alpha, team "Soulless", 22 members, queried 2026-09-09 through the Management API SQL runner):** no member is negative in the database. For every member `coin_balance + Σ(their open wagers) = Σ(their transactions)` — 100 onboarding grant + 5 per daily reward. 56 wagers on 6 pool bets (all `closed`, none resolved), 0 duels, 0 deleted bets, 0 injections. `place_wager`'s `p_amount > v_balance` gate held every time; nobody staked more than they were credited (the "105" is 100 grant + the first day's 5; five people legitimately earned a second 5 after 00:00Z and bet it). The `delete_bet` overdraw path — the previous theory — was never exercised, and no other server path can debit below zero (every RPC's gate re-read: `place_wager`, `create_duel`, `accept_duel`, `decline_duel`, `resolve_bet`, `claim_daily_reward`, `remove_membership`).

The negatives were on **other people's screens** — the leader's dashboard (open since 22:35Z, before anyone else joined at 23:42–23:56Z) and any tab left open; roster (`team-settings-modal.tsx`), Richest tab and wallet all read the same local `team.members`. A refresh makes them correct, which is why nobody reproduced it with a reload, and nothing self-heals a connected tab (no polling; `onResubscribe` reload only fires after a socket drop). Two realtime leaks, same shape: *the observer receives every debit but never the credit.*

1. **`member-insert` trusts a pre-grant snapshot.** `app.seed_membership` (`supabase/migrations/20260905140000_team_rpcs.sql:83-94`, never redefined; still called by `join_team_with_code` in `20260907150000_invite_links.sql:186`) inserts the `team_members` row with `coin_balance = 0` and only then credits the 100-coin grant through `app.apply_transaction` — a separate UPDATE statement, so logical decoding emits two events. The `team_members` INSERT binding shipped 2026-09-08 (`apps/web/src/lib/data/realtime.ts:320-332`) delivers the first one; `applyRemote`'s `member-insert` case (`apps/web/src/lib/team-context.tsx:1612-1637`) maps it verbatim via `toMember` and dispatches `add-member` at **0**. Every wager that member places afterwards arrives as `wager-insert` → `place-wager` reducer (`team-context.tsx:732`, `coinBalance - amount`, no floor) and drives the observer's copy to minus their whole stake. 21 of 22 members joined while the leader's dashboard was open — that's the "muitos players negativos", and −105 reads as "bet more than 105".
2. **Every ledger credit is invisible to observers.** `claim_daily_reward` (`20260905170000_resolution_rewards_ledger.sql:185`) and `inject_coins` (`team_rpcs.sql:285-309`) go through `app.apply_transaction` = a `team_members` UPDATE plus a `transactions` INSERT. Neither is subscribed (`design-realtime.md` §5 rule 3), `transactions` isn't even in the publication, and its RLS is own-or-manager anyway. So observers' copies lag by every credit; the five second-day rewards then bet → −5 even for members who were present at page load. The same leak makes a leader's `inject_coins` invisible to the *recipient's own* open tab until reload.

The client's money model ("apply the deltas the event implies, never subscribe to balance UPDATEs") is only correct while the client's delta math and the SQL agree on every path, and this is the second time they haven't (the first is the double-apply race recorded in `20260905190000_realtime_publication.sql`'s header). `placeWager` in `team-context.tsx:1901-1921` even ignores the `balance_after` the RPC already returns and re-derives the debit locally.

**Plan (recommended): balances become server-authoritative on every client.**

1. `apps/web/src/lib/data/realtime.ts`: 8th team-channel binding — `team_members` **UPDATE**, `filter: team_id=eq.${teamId}` (same shape as the `bets` UPDATE binding at 253-265; `payload.new` is the full row under the default replica identity, only `payload.old` is PK-only; RLS `team_members_select_same_team` scopes it to teammates). New `RemoteEvent` variant `member-update` carrying the `MemberRow`. No migration needed for this step: `20260908120000_team_members_realtime.sql` added the table with a plain `add table`, so UPDATE is already replicated — the client just doesn't bind it.
2. `apps/web/src/lib/team-context.tsx`: reducer case `member-update` — overwrite `coinBalance`, `profitLoss` and `role` from the row, absolute; ignore members this client doesn't hold (universal receive rule). No delta math.
3. Strip every local balance delta so nothing is ever applied *on top of* an absolute value (the double-apply race the docs feared only exists while both models coexist). Complete list, verified by grep — all in `team-context.tsx`: `place-wager` 732, `start-duel` 806, `accept-duel` 836, `resolve-bet` 758, `delete-bet` 776, `void-duel` 875, departure cascade 970-971; `applyRemote`'s `bet-update` (1519) and `bet-delete` (1541) stop passing `settleBet`/`reverseBet` deltas (they still flip bet state; `settleBet` stays for payout display in `bet-row.tsx` / `bet-detail-page.tsx` and in `consistency-guard.ts`). `applyDeltas` (583-599) becomes dead — delete it. Keep `add-transaction`'s absolute `balanceAfter` set (1066). For instant feedback the acting client sets its own `coinBalance = result.balanceAfter` from `place_wager` / `create_duel` / `accept_duel` (`bet-mutations.ts` already returns it for all three; `injectCoins`/`claimDailyReward` too). `resolve_bet` / `delete_bet` return deltas only, so the actor waits for its own UPDATE echoes (sub-second) — or extend those two RPCs to also return `balance_after` per member if the beat of lag reads badly. Ordering is safe: Realtime delivers in commit order, so a stale echo is overwritten by the next event; nothing accumulates.
4. `member-insert` ordering (`team-context.tsx:1635-1636` awaits `fetchUser` *before* dispatching `add-member`; `handleRemote` is fire-and-forget per event): an UPDATE for the joiner landing during that fetch — the grant, the first reward — would be dropped as "unknown member", and a wager the joiner places in that window is silently under-counted today (`patchMembers` finds nobody). Dispatch `add-member` synchronously with the row, then `fetchUser` and dispatch a **new** `add-user` action that appends to `data.users` (`update-user` at 1037-1041 only replaces, it cannot append). The blank-name window shrinks to one fetch round-trip and is covered by the existing "?" fallback user (~3140).
5. Small migration: `app.seed_membership` inserts with `coin_balance = app.onboarding_grant_coins()` and writes the `transactions` row itself (`balance_after` = grant) instead of insert-0-then-`apply_transaction` (which re-reads and increments, so it can't be reused here). Nothing objects: `enforce_team_member_update_rules` is `before update` only; `enforce_non_negative_balance` passes trivially on a positive insert; the one-grant partial unique index still sees one row. Makes the INSERT payload truthful on its own, independent of steps 1-4.
6. Docs and comments that state the rule being overturned — all of them: `agent-docs/design-realtime.md` §5 rule 3 (118-130, and the `team_members` sub-section 193-225; rule 4 "no `transactions`" stays) with the real budget — 22 rows × 22 tabs = 484 messages per resolution against 2M/month, i.e. the §2 scenario's 450 is 0.02% of quota; `agent-docs/design-scale-and-free-tier.md` §2.5 (~204); `supabase/README.md:246-250` (already stale — omits `chat_messages` and the INSERT exception); `supabase/migrations/20260905190000_realtime_publication.sql:42-56` ("WHAT IS DELIBERATELY OUT") and `20260908120000_team_members_realtime.sql`'s header; `realtime.ts` header; `team-context.tsx:531-540` (`add-member` action comment) and 1459-1465 (`applyRemote` doc block).
7. Consistency guard (`apps/web/src/lib/data/consistency-guard.ts`): it did **not** and cannot catch this class — for a leader it already checks every member (149), but its ledger term is the `data.transactions` snapshot from the last load, which misses the same UPDATE-only credits, so stored −105 and expected −105 agreed by construction. After the fix the opposite happens: server balance 0 vs stale local ledger → false positives in dev. Either refresh the member's ledger rows on `member-update` (one scoped query, leader/moderator only — they can read them) or narrow the `coinBalance` check to the viewer (whose own ledger is always complete via `add-transaction`) and keep `profitLoss` for everyone.
8. Resolution now arrives as N separate `member-update` events instead of one batched dispatch — standings re-sort N times within ~100 ms. Check it doesn't visibly flicker; coalesce dispatches per animation frame if it does.
9. Verify on hosted dev with two browsers (CDP recipe): A on the dashboard; B joins by invite → A shows B at 100 immediately; B claims the reward → A shows 105; B wagers 105 → A shows 0, never negative; leader injects into B → B's open tab updates; resolve a bet → A and B equal a fresh `loadTeamData`. Then push the migration to prod.

*Alternative kept for the record (smaller, keeps rule 3):* step 5 + publish `transactions`, loosen its select RLS to same-team, bind INSERT filtered by team_id and apply `balance_after` absolutely (the `add-transaction` reducer already does this) + step 4. Covers grant/reward/injection but keeps the delta model for wagers/resolutions — the part that just failed — and exposes teammates' ledgers. Not recommended.

*Nothing to repair in prod data.* Testers refresh and the numbers are right.

## Richest/poorest leaderboard wrong

**What live actually shows:** no bet has resolved yet, so `profitLoss` is 0 for all 22 members. The Poorest tab shows the empty state ("Todo mundo ainda tá no azul. Suspeito.") — correct for DOM-028 — while the Richest tab on a stale dashboard listed people at −105 (bug above). The contradiction was bug 1's, not this board's. The Poorest sort key being `profitLoss` is what `AGENT_SPEC.md` DOM-028 specifies ("biggest losers by profit/loss standing. Separate from DOM-027"); the `bottom5` badge (`team-context.tsx:3180-3181`), the `CoinDelta` rendering, the rust treatment (`design-visual-identity.md:148`) and the dry copy ("House's favorite donor") are all built on that meaning, and `packages/shared/src/types.ts:134` documents `profitLoss` as the field that "feeds the podium of the poor".

Real defects in the board, independent of bug 1:

- **Filler rows.** The lists aren't filtered to losers. The moment one member has negative P/L, `allSolvent` flips off and `standings-module.tsx:111` shows the top 5 by P/L ascending — ranks 2–5 filled with members at "+0" (or winners at "+12", in jade) under the rust "Poorest" heading; `standings-full-modal.tsx:28` lists all 22, winners at the bottom. The badge code already filters `profitLoss < 0`; the lists don't.
- **Arbitrary ties.** Both sorts are stable over join order (`team-data.ts:691-693` and the `add-member` reducer both sort by `joinedAt`), so equal balances (all the 105s today) and equal P/L rank by who joined first. Rank 1 among ties is whoever joined earliest.
- **Label ≠ metric.** "Poorest / Mais pobres" reads as lowest balance; the board measures realized losses, so a member at balance 0 with everything staked on open bets isn't "poor" here.
- No test covers any of this: the richest/poorest/`bottomFive`/`rankBadgeFor` derivation is inline in a `useMemo` (`team-context.tsx:3177-3192`), not a function; `packages/shared`'s six test files never touch it.

**Decision needed (product), then a small fix either way:**

- **A. Keep DOM-028 (realized-loss podium) — recommended.** In a game where people go all-in on open bets, a bottom-5 by balance would just list whoever has the most coins staked right now; the loss board is the one with meaning, and everything downstream (badges, copy, colors, `CoinDelta`) already assumes it. Steps: (1) extract a pure `deriveStandings(members)` (in `packages/shared`, next to `settlement.ts`) returning `richest`, `poorest`, `bottomFive`: `poorest = members.filter(m => m.profitLoss < 0)` sorted P/L asc, then `coinBalance` asc, then `joinedAt`; `richest` sorted `coinBalance` desc, then `profitLoss` desc, then `joinedAt`; `bottomFive = poorest.slice(0, 5)`; unit-test the tie-breaks and the one-loser case; `team-context.tsx:3177-3182` calls it. (2) `standings-module.tsx:117` / `standings-full-modal.tsx:29`: `allSolvent = poorest.length === 0`. (3) `messages/en.json` + `pt-BR.json`, exactly two keys each: `standingsModule.poorest` (225) and `standingsFullModal.poorest` (367) → what it measures — "Biggest losers" / "Maiores perdedores" (or "No vermelho"); `donorNote`/`empty`/`rankBadge.bottom5` stay. (4) `design-dashboard.md:50`: new label, and fix "all-zero P/L → empty state" to "nobody negative" — the code deliberately uses `>= 0` (`standings-module.tsx:112-116`). (5) Verify on dev by resolving one bet: podium shows only losers, no filler, badges match.
- **B. Mirror Richest (balance ascending).** Sort key at 3178 → `a.coinBalance - b.coinBalance` (same tie-breaks and extraction as A), render `CoinAmount` instead of `CoinDelta` in both surfaces, drop `allSolvent`/"donor" copy (always populated), rebase the `bottom5` badge on balance, and rewrite DOM-028 plus the DOM-029 assumption in `AGENT_SPEC.md`, `design-dashboard.md` §4.2, `design-visual-identity.md:148` and 684 (Poorest tab / poor podium rust callouts), and the `profitLoss` comment in `packages/shared/src/types.ts:134`. Loses the realized-loss board entirely.

Separate, only if wanted: "Richest" ranks by `coinBalance` (DOM-027 "by current balance"), which excludes open stakes — in the alpha the three members who never bet topped it and the all-in players sat at 0. A "balance + open stake" ranking is a spec change, not a bug.
